# ТЗ — модуль «Закупки»

Дочерний документ к `docs/PROJECT_BRIEF.md`. Здесь — только то, что касается
модуля торгов (Закупки/Продажи): списки, карточка процедуры, спецификация.
Общая архитектура площадки (мессенджер целиком, компании, онбординг) —
в основном брифе, здесь только точки соприкосновения.

Модель данных — `prisma/schema.prisma`, модели `Procedure`, `SpecificationItem`,
`Proposal`, `ProposalItem`, `Checklist`, `ChecklistItem`, `Document`, `Favorite`.

## 0. Структурные референсы — читать перед версткой

Список и карточка процедуры **намеренно копируют информационную архитектуру**
двух реальных продуктов. Не визуальный стиль (цвета/шрифты/бренд — свои), а
именно устройство экрана: из чего он состоит и как эти части взаимодействуют.

- **Список закупок** → структура как у [Bidzaar](https://bidzaar.com/app/requests/public/buy)
- **Карточка процедуры (вкладка «Общая информация»)** → структура как у
  карточки задачи в Битрикс24 (`/company/personal/user/1/tasks/task/view/N/`)

Если в этом файле описание какого-то элемента звучит неоднозначно —
приоритет у структурного паттерна референса, а не у домысливания по
аналогии с другими SaaS-таблицами/карточками. Ниже в разделах 4 и 6 —
явный чек-лист, что конкретно заимствовано, чтобы это можно было
проверить пункт за пунктом, а не угадывать по ощущению.

---

## 1. Назначение

Организатор проводит закупку или продажу товаров/услуг: публикует процедуру
со спецификацией, участники подают предложения, организатор при необходимости
запускает переторжку и выбирает победителя. Без 44-ФЗ/223-ФЗ — только
коммерческие торги.

## 2. Роли

| Роль | Определение |
|---|---|
| Организатор | сотрудник компании, которая создала процедуру (`Procedure.organizerId`) |
| Участник | сотрудник компании, подавшей предложение (`Proposal.companyId`) |
| Гость | пользователь без компании ИЛИ компания, не связанная с этой процедурой |

Действует поверх общей модели `User` ↔ `CompanyMember` ↔ `Company` — участие
в процедуре определяется компанией, не конкретным пользователем.

**Dev-инструмент:** переключатель ролей на странице процедуры (Организатор /
Участник / Гость) — подменяет, какие данные подгружать, без реальной
авторизации под другой ролью. Только для разработки, убрать перед продом.

## 3. Жизненный цикл процедуры

```
Черновик → Опубликовано → [Переторжка]* → Выбор победителя → Завершено → [Документооборот]*
```
`*` — опциональные этапы. Статус — `Procedure.status : ProcedureStatus`.
«Проверка» (7-й статус из ранней идеи) исключена из MVP — нет ролей/приглашений,
проверять нечем.

**Переходы — кнопки действий, не dropdown статусов.** Из каждого статуса
показываем только доступные переходы, а не полный список ProcedureStatus:

| Текущий статус | Доступные действия |
|---|---|
| DRAFT | Опубликовать |
| PUBLISHED | Начать переторжку · Перейти к выбору победителя |
| RETRADE | Новый раунд переторжки · Перейти к выбору победителя |
| WINNER_SELECTION | Завершить (после выбора победителя в мессенджере) |
| COMPLETED | Открыть документооборот |
| DOCUMENTS | — (конечный статус) |

Каждый переход пишет структурированное системное сообщение в тред SYSTEM
этой процедуры (карточка: что изменилось / кто / когда — не строка текста).

## 4. Списки процедур

### Структурная ДНК из Bidzaar (проверяемый чек-лист)

- [ ] Элемент списка — **карточка**, не строка таблицы
- [ ] Фильтры — **список независимо разворачиваемых строк** (каждый фильтр
      сам по себе, у своей строки), НЕ единая модалка/drawer «Фильтры» со
      всеми полями сразу
- [ ] Поиск, счётчик найденных и сортировка — **в одной шапке**, над
      фильтрами, не разнесены по разным местам экрана
- [ ] Внутри карточки — **два яруса информации**: (1) номер+название+бейдж
      статуса на верхней строке, (2) организатор+регион+теги на второй,
      (3) дедлайн+число лотов на третьей — не единый плоский блок текста
- [ ] Сортировка — простой переключатель из 1-2 понятных вариантов
      (дата публикации / дедлайн), не конструктор сортировки
- [ ] Избранное — иконка звезды прямо на карточке, не отдельное действие
      через меню

Три разных списка на одном переиспользуемом компоненте с разным query:

| Список | Условие выборки |
|---|---|
| «Мои процедуры» | `organizerId` = текущая компания, все статусы включая DRAFT |
| «Участие в процедурах» | есть `Proposal` от текущей компании |
| «Закупки» / «Продажи» (витрина) | `status != DRAFT`, `type = PURCHASE / SALE`, независимо от компании |

**Фильтры витрины** (по образцу Bidzaar): организатор, регион поставки
(`deliveryRegion`), теги (`tags`), статус, дата публикации, окончание приёма
предложений (`deadlineAt`). Поиск по названию. Сортировка по умолчанию —
дата публикации, убывание.

**Избранное** (`Favorite`) — реализуется по-настоящему, не заглушка: тумблер
«★ Только избранное» + значок на карточке.

**Не в MVP, но зарезервировано на витрине:**
- тумблер «ИИ-рекомендации» — заглушка, подключается к общему ИИ-контексту позже
- кнопка «Подписаться» на набор фильтров — сохраняет фильтр, сама рассылка
  уведомлений не в этом заходе

**Карточка процедуры в списке:**
- номер (`Procedure.number`, человекочитаемый, не uuid) + название
- бейдж статуса, цвет по семантике: PUBLISHED → success, RETRADE → warning,
  WINNER_SELECTION → accent, COMPLETED → нейтральный
- организатор + синяя галочка верификации, если `Company.isVerified`
- регион + теги
- дедлайн в формате «до 18.08, 14:52 (осталось 9 дней)», не просто дата
- число лотов

## 5. Страница процедуры — структура

Сверху вниз:
1. Номер + название, переключатель ролей (dev)
2. Степпер жизненного цикла — 6 шагов из раздела 3
3. Вкладки: **Общая информация** · **Спецификация** · **Документы**

Мессенджер — **не вкладка**. Это уже существующий глобальный докнутый
компонент (см. основной бриф), на странице процедуры просто отфильтрован
по `procedureId`.

## 6. Вкладка «Общая информация»

По образцу карточки задачи Битрикс24 (живой разбор, не только вёрстка).

### Структурная ДНК из Битрикс24 (проверяемый чек-лист)

- [ ] Мессенджер процедуры — **постоянная соседняя панель**, видимая всегда
      при просмотре карточки, НЕ вкладка и не модалка по клику (уже так
      зафиксировано в разделе 5, здесь — тот же принцип, просто явно)
- [ ] Метаданные (Компания/Создал/Даты) — **вертикальный список строк
      «лейбл слева — значение справа»**, НЕ сетка карточек и НЕ таблица
      с колонками
- [ ] Статус — **контрол с глаголами-действиями** («Начать переторжку»),
      НЕ выпадающий список всех значений статуса (см. раздел 3)
- [ ] Дополнительные блоки (чек-лист и т.д.) при заполнении **встраиваются
      в ту же панель**, между метаданными и рядом кнопок — НЕ уводят на
      отдельную страницу и не открываются в модальном окне
- [ ] Любое изменение карточки (новый пункт чек-листа, смена статуса) —
      **отдельная запись в мессенджере процедуры**, а не только при
      создании — лог, а не разовое событие

**Блок информации сверху:**
1. Наименование процедуры
2. Описание
3. Компания (организатор)
4. Создал — конкретный пользователь от лица компании (`Procedure.createdById`)
5. Дата публикации (`publishedAt`)
6. Дата выбора победителя — плановая, задаётся организатором
   (`winnerSelectionAt`, отдельно от `deadlineAt`)

**Ряд кнопок дополнительных блоков снизу:** Опросный лист · Приглашение
компаний · Файлы · Переторжка · Ещё.

Кнопка «Переторжка» здесь — точка входа-заглушка, НЕ дублирует реальную
логику: настоящий запуск нового раунда — только на вкладке «Спецификация»
(раздел 7).

«Приглашение компаний» — приватные процедуры по приглашению, не только
публичные. Модель данных под это — отдельная задача, в MVP только кнопка.

### Механика блоков — единая для всех, без исключений

(Осознанно НЕ повторяем непредсказуемость Битрикс24, где один блок — поповер,
другой — подмена всей панели.)

1. Пустое состояние — кнопка в нижнем ряду.
2. Клик → инлайн-раскрытие компактной формы добавления прямо в карточке,
   на месте будущего блока. Никогда не поповер у кнопки, никогда не подмена
   всей панели.
3. После первого элемента блок становится постоянной секцией **над** рядом
   кнопок: заголовок, счётчик/прогресс, содержимое, строка добавления внизу.
4. Кнопка внизу переходит в активное визуальное состояние; повторный клик
   скроллит/сворачивает к блоку, не открывает добавление заново.
5. Каждое изменение блока → структурированное системное сообщение в тред
   SYSTEM.

**Единственный реальный блок в MVP — Чек-лист** (`Checklist`/`ChecklistItem`):
название, пункты с чекбоксами, инлайн-добавление пункта, прогресс «N/M
выполнено». Дешёвый в реализации (без файлового хранилища и конструктора
форм) и был первым примером «своих блоков» в исходной идее продукта.

Опросный лист, Приглашение компаний, Файлы — кнопки-заглушки с тултипом
«Скоро» по наведению. Встроятся по той же механике, когда дойдёт очередь.

## 7. Вкладка «Спецификация»

**Обязательные поля лота** (`SpecificationItem`): наименование, количество,
единица измерения, ставка НДС, цена без НДС, цена с НДС, стоимость без НДС,
стоимость с НДС, характеристика, условия доставки. Конструктор дополнительных
полей — вне MVP.

**Заполнение:**
- Организатор — на этапе DRAFT, вручную или загрузкой Excel с
  ИИ-распознаванием (заполняет поля по строкам файла).
- Участник — на этапе PUBLISHED, построчно повторяет структуру организатора
  своими значениями (`Proposal` + `ProposalItem`, привязка к
  `SpecificationItem`).

**Переторжка:** новый раунд = новый `Proposal` с `round + 1` для ещё не
заблокированных участников. История прошлых раундов не удаляется.

### Матрица видимости по роли и этапу

| Этап | Организатор | Участник | Гость |
|---|---|---|---|
| Черновик | полное редактирование + загрузка Excel | не видит | — |
| Опубликовано | своя спецификация (лок на правку), список подавших | спецификация организатора + форма предложения построчно | только «Общая информация» |
| Переторжка | сравнительная таблица: своя цена + предложения всех участников по раундам, лучшая цена подсвечена | своё последнее предложение, можно обновить | — |
| Выбор победителя | та же сравнительная таблица; само решение — действие в мессенджере, не в таблице | статус «на рассмотрении» | — |
| Завершено | таблица с выделенным победителем | статус «выиграл» / «проиграл» | — |
| Документооборот | загрузка файлов (заглушка) | просмотр/загрузка (заглушка) | — |

Гость не видит цены и участников ни на одном этапе.

**Кнопка «Новый раунд переторжки»** — только у организатора на этапе
RETRADE. Выбор победителя (`Proposal.isWinner`) НЕ делается через таблицу —
только отдельным действием в мессенджере.

## 8. Вкладка «Документы»

MVP: загрузка/просмотр файлов без юридической значимости (`Document`).
ЭЦП и юридически значимый документооборот — вне MVP.

## 9. Сводная таблица: реально vs заглушка

| Функция | В MVP |
|---|---|
| Жизненный цикл процедуры (без «Проверки») | ✅ реально |
| Спецификация + Excel-загрузка (без ИИ-парсинга) | ✅ реально |
| Предложения участников, переторжка | ✅ реально |
| Список закупок/продаж + фильтры + избранное | ✅ реально |
| Чек-лист на карточке процедуры | ✅ реально |
| ИИ-парсинг Excel, автогенерация ТЗ, скоринг | ⏳ отдельная задача (промпты) |
| Опросный лист | ⛔ заглушка с тултипом |
| Приглашение компаний | ⛔ заглушка с тултипом |
| Файлы на карточке (вкладка «Общая информация») | ⛔ заглушка с тултипом |
| ИИ-рекомендации в списке | ⛔ заглушка (тумблер) |
| Подписка на фильтр | ⛔ заглушка (сохранение без рассылки) |

| Конструктор доп. полей спецификации | ⛔ вне MVP |

## 10. Открытые вопросы

1. Промпты для ИИ-функций (генерация ТЗ, парсинг Excel, скоринг, протокол) —
   не написаны, отдельная задача.
2. Формат хранения истории раундов переторжки в UI (не в схеме — она уже
   поддерживает через `round`) — как показывать пользователю историю.
3. Модель данных под «Приглашение компаний», когда дойдём до реализации.
