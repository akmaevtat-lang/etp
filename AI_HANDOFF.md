# AI Handoff — ЭТП

Актуальный контекст для продолжения разработки электронной торговой площадки. Обновлено 2026-08-14 по текущему коду и состоянию git.

## Порядок источников истины

1. Текущий код — источник истины о том, что фактически реализовано.
2. Этот `AI_HANDOFF.md` — актуальные решения владельца продукта и состояние работы.
3. `docs/TZ_ZAKUPKI.md` — детальные требования к модулю закупок.
4. `docs/PROJECT_BRIEF.md` — общая продуктовая концепция и границы MVP.

Код не имеет права автоматически отменять зафиксированное продуктовое требование. Если требования и код расходятся, сначала сообщить владельцу продукта; не исправлять бизнес-логику и не выбирать спорный вариант самостоятельно.

Перед любыми изменениями также прочитать корневой `AGENTS.md`.

## Актуальные продуктовые решения

- Площадка предназначена для коммерческих закупок и продаж, без логики 44-ФЗ/223-ФЗ.
- В процедурах и предложениях участвует компания, а не пользователь напрямую. Пользователь действует через `CompanyMember`.
- Пользователь без компании может просматривать открытые процедуры, но не может участвовать. Участие возможно только от имени компании. Текущий код публичный просмотр ещё не обеспечивает — это незакрытое расхождение, а не отмена требования.
- Жизненный цикл процедуры: `DRAFT → PUBLISHED → RETRADE → WINNER_SELECTION → COMPLETED → DOCUMENTS`. Этап проверки исключён из MVP.
- Завершение процедуры должно происходить после выбора победителя.
- Выбор победителя проектируется как отдельное действие через мессенджер, а не через сравнительную таблицу.
- История переторжки хранится отдельными `Proposal` по раундам; `Proposal.round` увеличивается, прошлые раунды не удаляются.
- Системный журнал в целевой реализации должен быть структурированным: событие, автор, время и связанный контекст. Текущие строки в `Message.content` — промежуточная реализация.
- AI на текущем продуктовом этапе только предлагает текст. Он не создаёт, не изменяет и не удаляет бизнес-сущности напрямую.
- Человекочитаемый номер процедуры присваивается при первой публикации; у черновика номера нет.
- Избранное персонально для пользователя, а не для компании.
- Текущий визуальный стиль после коммита `6d34884` является базовым до отдельного задания на редизайн.

## Стек и архитектурная база

- Next.js 16.2.12, App Router, React 19, TypeScript strict.
- Tailwind CSS 4.
- shadcn/ui с актуальным preset `base-nova`, база компонентов — Base UI, иконки — Lucide. Это не Radix API: для composition используется `render`, а не `asChild`.
- PostgreSQL через Prisma 6.19.3 и `@prisma/client` 6.19.3.
- Supabase Auth и SSR-клиенты Supabase; `Prisma.User.id` совпадает с Supabase Auth user id.
- pnpm; `postinstall: prisma generate` обязателен для корректной сборки на Vercel.
- Anthropic SDK подключён напрямую в `lib/ai/`.
- Хостинг: Vercel, база и Auth: Supabase Cloud.
- Это одно Next.js-приложение: серверные операции в основном реализованы через Server Actions, отдельного backend-сервиса нет.

Ключевая модель доступа: пользователь может состоять в нескольких компаниях, активная компания хранится в cookie `active_company_id`. Бизнес-действия выполняются в контексте активной компании.

## Полностью реализовано в текущем коде

### Аккаунты и компании

- Регистрация, вход и выход через Supabase Auth.
- Создание первой компании через onboarding.
- Создание дополнительных компаний.
- `User ↔ CompanyMember ↔ Company` many-to-many.
- Переключение активной компании в сайдбаре.
- Автоматическое создание company-level тредов `AI` и `SYSTEM` для новой компании.

### Dashboard и навигация

- Dashboard компании с карточкой компании, показателями, количеством процедур, участий, побед, черновиков, объёмом и избранным.
- Блоки активных закупок и продаж.
- Основной сайдбар: Главная, Мои процедуры, Участие, Приглашения, Заявки из каталога, Настройки и сервисы Закупки/Продажи/Каталог.
- Приглашения, каталог, заявки из каталога и настройки пока остаются заглушками.

### Списки процедур

- Единый query/UI-слой для `/procedures`, `/participation`, `/marketplace/purchases`, `/marketplace/sales`.
- Карточки процедур, поиск, сортировка, фильтры по организатору, региону, тегам, статусу и датам.
- Фильтры хранятся в URL search params.
- Персональное избранное и фильтр «Только избранное».
- Адаптивная панель фильтров: desktop-aside и тот же контент в `Sheet` на ширине `<lg`.
- Меню карточки «Открыть / Скопировать ссылку / Удалить»; удаление доступно только для черновика и очищает зависимости в транзакции.

### Создание и карточка процедуры

- Актуальное основное поведение: пункт «Закупка» в `CreateProcedureMenu` вызывает `createDraftPurchase()`, создаёт пустой `PURCHASE`-черновик и сразу переводит пользователя в редактируемую карточку. Промежуточная форма не используется в основном потоке.
- Пункт «Продажа» в меню отключён и помечен «Скоро».
- Старый маршрут `/procedures/new` всё ещё существует и позволяет создать `PURCHASE` или `SALE`; его окончательная судьба не решена.
- Карточка процедуры — одна вертикальная страница без степпера и вкладок.
- На `DRAFT` организатор редактирует название, описание, место поставки, дедлайн и плановую дату выбора победителя.
- После публикации данные отображаются read-only.
- Метаданные показываются вертикальными строками.
- Спецификация вынесена в `/procedures/[id]/specification` и представлена на основной странице карточкой-сводкой.
- Номер процедуры присваивается только при публикации через `MAX(number) + 1`.

### Спецификация и первое предложение

- Ручное создание, редактирование и удаление позиций спецификации организатором на `DRAFT`.
- После публикации спецификация организатора read-only.
- Участник на `PUBLISHED` подаёт построчное предложение: цена и комментарий по каждой позиции.
- Создаются реальные `Proposal` и `ProposalItem[]` с `round = 1`.
- Повторная подача первого предложения блокируется.
- Организатор видит список подавших компаний и время подачи.
- После подачи создаётся `PARTICIPANT`-тред и системное событие.

### Чек-лист

- Создание чек-листа, добавление пунктов, переключение выполнения и расчёт прогресса.
- Блок раскрывается инлайн и после создания остаётся постоянной секцией карточки.
- Изменения пишутся в процедурный SYSTEM-тред.

### Глобальный мессенджер

- Мессенджер находится на уровне dashboard layout и доступен на всех внутренних страницах.
- Состояние открыт/закрыт хранится в `localStorage`.
- На `lg+` это докнутая правая панель; на меньших экранах — fixed overlay с backdrop.
- Навигация организатора: общий инбокс → группа чатов процедуры → конкретный чат.
- Участник из группы процедуры может сразу перейти в свой единственный `PARTICIPANT`-чат.
- Company-level `AI` и `SYSTEM` показываются плоскими строками; процедурные треды группируются по процедуре.
- В счётчик группы сейчас входят видимые `PARTICIPANT`-треды и процедурный `SYSTEM`-тред.
- `MessengerProcedureScope` фильтрует панель по процедуре на основной странице и странице спецификации.
- Процедурный `SYSTEM`-тред содержит журнал создания, изменений, переходов статуса, чек-листа и подачи предложения.
- Список тредов и сообщения обновляются polling-ом; Supabase Realtime сознательно не используется в текущем MVP.
- В SYSTEM-тред писать вручную нельзя.

### AI-чат

- AI-тред получает контекст до 20 последних процедур компании и их спецификаций.
- Ответ Anthropic сохраняется как сообщение с `senderId: null`.
- При пустом `ANTHROPIC_API_KEY` возвращается объясняющая заглушка без падения UI.
- Системный prompt запрещает AI изменять данные площадки напрямую.

### Лендинг и базовый визуальный стиль

- Реализован новый маркетинговый лендинг на shadcn с Bitrix24-inspired blue hero и фотографиями людей.
- После нескольких итераций убран subtitle hero, скорректированы размеры и скругление фотографий.
- Коммит `6d34884` установил базовый стиль приложения: фон `#EDF2F4`, общий radius `1rem`, белые карточки без рамок с лёгкой тенью, hover-тень у карточек процедур и белую поверхность мессенджера.

## Частично реализовано

- Жизненный цикл: статусы и переходы существуют, но реальной переторжки и выбора победителя нет.
- Переход `WINNER_SELECTION → COMPLETED` технически возможен без `Proposal.isWinner`; это не соответствует актуальному продуктовому требованию.
- Схема поддерживает `Proposal.round`, но UI и actions работают только с `round = 1`.
- Организатор видит список подавших компаний, но не сравнительную таблицу цен по позициям и раундам.
- Системный журнал существует, но хранится и отображается как обычный текст, а не структурированное событие.
- Модель `Document` существует, но UI и Storage для файлов отсутствуют.
- `Company.isVerified` существует, но UI управления нет; значение меняется вручную в БД.
- `CompanyRole.ADMIN/EMPLOYEE` существует, но точное разграничение разрешений не реализовано.
- `ProcedureType.SALE` поддерживается схемой и старым маршрутом, но основной UI создания продаж отключён.
- `/inbox` остаётся страницей-заглушкой, хотя реальный инбокс доступен в глобальной панели.
- AI-клиент и company assistant существуют, но прикладные AI-функции закупок не реализованы.
- Публичная маркетинговая страница доступна без компании, но открытые реальные процедуры без компании пока просматривать нельзя.

## Зафиксированные UX-решения

- Структура списков ориентируется на Bidzaar: карточки, вертикальная панель независимо раскрываемых фильтров, простой выбор сортировки, звезда избранного на карточке.
- Поиск и сортировка находятся вверху панели фильтров; счётчик найденных — над списком карточек. Это согласованное отклонение от исходного референса.
- Структура карточки процедуры ориентируется на task-card pattern Битрикс24, но визуальный стиль собственный.
- Страница процедуры остаётся единой вертикальной страницей; возвращать вкладки или lifecycle stepper без отдельного задания нельзя.
- Статус меняется действиями-глаголами, не dropdown всех статусов.
- Дополнительные блоки раскрываются инлайн, а заполненный блок остаётся внутри карточки.
- Спецификация остаётся отдельным маршрутом.
- Мессенджер остаётся глобальной соседней панелью, не вкладкой и не самостоятельным модальным сценарием.
- Визуальный baseline после `6d34884` не менять без задания на редизайн.

## Расхождения между кодом и требованиями

Эти расхождения не исправлять автоматически:

1. Требование разрешает пользователю без компании просматривать открытые процедуры; текущие marketplace/procedure routes вызывают `requireCompany()`.
2. Требование ограничивает гостя общей информацией и запрещает ему видеть цены и участников; текущий код считает любого не-организатора потенциальным участником и показывает ему спецификацию опубликованной процедуры.
3. Завершение должно происходить после выбора победителя; текущий transition не проверяет `Proposal.isWinner`.
4. Выбор победителя должен быть действием в мессенджере; такого действия нет.
5. Переторжка должна создавать новые раунды `Proposal`; текущий код работает только с первым раундом.
6. Целевой системный журнал должен быть структурированным; текущий журнал — строки `Message.content`.
7. Основное создание закупки уже пропускает `/procedures/new`, но старый маршрут сохранился и позволяет создать продажу в обход disabled-пункта меню.
8. В брифе мессенджер описан как двухуровневый; текущая согласованная реализация для организатора трёхуровневая.
9. В раннем брифе карточка процедуры описана вкладками; более новое ТЗ и текущий код фиксируют единую страницу и отдельный маршрут спецификации.
10. Документы и Excel по-разному отнесены к MVP в разных разделах документов; решения владельца пока нет.

## Технические ограничения и известные грабли

- Не обновлять Prisma до 7 без отдельной задачи. Текущая схема использует `url = env("DATABASE_URL")` и `directUrl`.
- Не удалять `postinstall: prisma generate`.
- После `prisma db push`, меняющего схему, перезапускать локальный `next dev`: запущенный процесс может удерживать старый Prisma Client.
- Пулер Supabase иногда даёт transient connection error. Клиентские вызовы Server Actions должны обрабатывать ошибки через `try/catch`, чтобы не ронять экран.
- Next.js 16 использует корневой `proxy.ts`, не `middleware.ts`.
- Base UI `Button` использует `render`; если корневой элемент не `<button>`, указывать `nativeButton={false}`.
- Base UI `Select` должен получать `items`, иначе `SelectValue` может показать сырое значение.
- В `components/ui/sidebar.tsx` у `SidebarInset` необходим `min-w-0`, иначе широкие таблицы ломают layout.
- Элементы dropdown должны находиться внутри соответствующей group-композиции Base UI.
- При крупных функциях сначала сверить требования и подготовить план, затем двигаться этапами «схема → данные → UI → интеграции».
